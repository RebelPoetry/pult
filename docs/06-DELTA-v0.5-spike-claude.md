## 1. Сеть: новое правило (заменяет «профиль сети» в DELTA v0.3 §4 и v0.4 §4)
Хронология 21.09: (а) прогон владельца — локальный прокси 10808 был выключен, обвязка жёстко слала `claude` в него: каждый ход ~10 повторов за ~149 с, ноль токенов, все вердикты ложные;
(б) после починки обвязка пошла «напрямую», и примерно в 15:30–15:45 ВСЕ запросы аккаунта (и `claude -p` обвязки, и посторонние сессии) получали
`api_error`: «Your organization has disabled Claude subscription access for Claude Code · Use an Anthropic API key instead, or ask your admin to enable access». Отказ временный: с поднятым VPN тот же аккаунт работает.
Причина не доказана; совпало с окном без VPN. (в) За один час наблюдались оба расхождения: порт 10808 ОТКРЫТ, а туннель мёртв (503, ошибки TLS); порт ЗАКРЫТ, а выход — Германия (VPN в TUN-режиме мимо локального порта).
Правила:
- Состояние порта НЕ говорит о состоянии VPN ни в одну сторону. Единственная проверка — СТРАНА ВЫХОДА тем же путём, которым пойдёт дочерний процесс: `https://api.anthropic.com/cdn-cgi/trace` → строка `loc=XX`
  (через прокси, если профиль «прокси»; напрямую, если «напрямую»). Около 200 мс.
- Проверка выполняется ПЕРЕД первым ходом сессии и перед любым ходом после простоя дольше 60 с. Страна из списка-стража или неизвестна → ход НЕ запускается, нода получает статус «блок: сеть», ничего не тратится.
  Список-страж консервативный (RU, BY, CN, IR, KP, SY, CU) — это предохранитель Пульта, не официальный список Anthropic. Хранится в `~/.pult/config.json`, правится пользователем.
- Режимы профиля на провайдера: `auto` (прокси, если через него реально проходит запрос, иначе напрямую) · `required` (только через прокси, иначе блок) · `off`. Во ВСЕХ режимах действует страж страны выхода.
  Проба прокси — настоящий запрос через него, не TCP-коннект к порту.
- Текст ошибки `/disabled Claude subscription access/` классифицируется как «аккаунт или регион»: провайдер останавливается ЦЕЛИКОМ, без повторов, плашка «проверь VPN»; возобновление — после успешной проверки выхода.
  То же правило по смыслу — для Codex и opencode, когда появятся их тексты.
- `claude` при мёртвом прокси сам НЕ останавливается: 10 событий `system/api_retry` за ~149 с и тишина. Потолок адаптера: 3 подряд `api_retry` → прервать ход (в обвязке это 2,8 с вместо 3 минут).
  Поля события: `attempt`, `max_retries`, `retry_delay_ms`, `error_status`, `error`.
- Прокси-переменные `claude` учитывает (мёртвый порт ломает ход, первый `api_retry` через 459 мс). Путь `claude` через HTTP-вход порта 10808 так и НЕ измерен: порт каждый раз был закрыт. Остаётся «по документации».
- `pult doctor` и индикатор в окне показывают: режим профиля, страну выхода, время последней проверки.

## 2. Claude Adapter: измеренные факты (Claude Code 2.1.278)
- Виды событий успешного хода: `system/init`, `system/status`, `system/thinking_tokens`, `stream_event/{message_start, content_block_start, content_block_delta, content_block_stop, message_delta, message_stop}`,
  `assistant`, `rate_limit_event`, `result`. Поля `result`: `is_error`, `terminal_reason` (`completed` | `api_error`), `num_turns`, `duration_ms`, `total_cost_usd`, `usage{input_tokens, cache_creation_input_tokens,
  cache_read_input_tokens, output_tokens}`, `permission_denials`, `subagent_stats`, `modelUsage`, `stop_reason`, `ttft_ms`. Судить по `is_error` и `terminal_reason`, не по `subtype`.
- ЛИМИТЫ: статус-строка под `-p` НЕ вызывается вообще — этот план отменён. Источник — событие `rate_limit_event`, одно на ход, после последнего `assistant` и перед `result`:
  `rate_limit_info{status: "allowed", rateLimitType: "five_hour", resetsAt (unix-секунды), unifiedWindows.five_hour{utilization 0..1, resetsAt}, unifiedWindows.seven_day{utilization, resetsAt},
  isUsingOverage, overageStatus, overageDisabledReason}`. Оба окна в одном событии. В документации события нет; измерение сильнее ресёрча. Строки «You've hit your session limit…» остаются запасным признаком.
- РАЗРЕШЕНИЯ (`--permission-prompt-tool mcp__<сервер>__<инструмент>`, в спайке `mcp__pultask__ask`): аргументы вызова `{tool_name, input, tool_use_id}`; `input` для Edit — `file_path, old_string, new_string, replace_all`,
  для Bash — `command, description`. Отказ `{"behavior":"deny","message":…}` → файл не тронут, инструмент попадает в `result.permission_denials`, ход НЕ ошибка (`is_error: false`). Разрешение
  `{"behavior":"allow","updatedInput":{…}}` → правка применена. Bash с записью (`touch`) спрашивает; безобидный Bash выполняется без запроса — в Inbox попадает только то, что действительно требует решения.
  Сам инструмент разрешений НЕ виден в списке `tools` события `system/init`, хотя MCP-сервер в статусе `connected` — не использовать этот список как проверку готовности.
- RESUME: `--resume <uuid>` после SIGKILL — тот же `session_id`, контекст цел.
- СУБАГЕНТЫ: инструмент называется `Agent` (не `Task`), вход содержит `subagent_type`. События ребёнка — `assistant` с `parent_tool_use_id` = id вызова. В `result` есть `subagent_stats{spawned, started_in_background, max_depth}`.
  Вердикт «частично»: приход ТЕКСТА ребёнка под `--forward-subagent-text` не проверен, и субагент стартовал в фоне — ход `-p` закончился раньше него.
- СХЕМА: `--json-schema` → `result.structured_output`, работает.
- ВОРКФЛОУ РЕПЛИКОЙ: `Run /<имя> with args {…}` → модель вызывает инструмент `Skill {skill, args: "<JSON-строка>"}`, затем `Workflow {name, args: {объект}}`. Нужны ОБА правила: `--allowedTools "Skill(<имя>)" "Workflow(<имя>)"`.
  Результат инструмента — «Workflow launched in background», ход `-p` сразу заканчивается: событий агентов воркфлоу в потоке 0, итогового значения нет. Вердикт «частично»: запуск доказан, наблюдение и итог — нет.
- ЦЕНА СТАРТА: в проекте Me с обычными настройками первый ход — 41,6 тыс. токенов контекста (115 скиллов, 150 команд, 50 агентов); в песочнице с `--setting-sources user` — 23,3 тыс. (37 / 72 / 12).
  Разница ~18 тыс. токенов (44 %). Замер нечестный по кэшу (первый — холодная запись, второй — чтение), поэтому это порядок величины, не точная цифра. Базовый системный промпт ≈ 23 тыс. даже в дешёвом профиле.
- ТЁПЛАЯ СЕССИЯ: после 2, 5, 9, 20, 40 и 60 минут простоя процесс жив, второй ход `is_error: false`; задержка 1310/1760/1846 мс (2/5/9 мин) и 2136/2129/2681 мс (20/40/60 мин); кэш промпта тёплый и через час
  (`cache_read_input_tokens` 23330/23330/23343, `cache_creation_input_tokens` только 1378/1373/1319). Первый ход вместе со стартом процесса — 2,6–3,5 с (короткий прогон) и 4,0–4,8 с (ночной прогон).
  Источники: `logs/s1-warm-ttl.short-2-5-9.jsonl` (2/5/9 мин), `logs/s1-warm-ttl.jsonl` (20/40/60 мин).

## 3. Два вывода, которые меняют дизайн
- «ХОД ЗАВЕРШЁН» ≠ «РАБОТА ЗАВЕРШЕНА». Под `-p` и субагент, и воркфлоу могут уйти в фон, а `result` приходит сразу. Адаптер Claude: если `subagent_stats.started_in_background > 0` или в ходе был вызов `Workflow`,
  нода НЕ закрывается по `result` — сессия остаётся открытой (stdin не закрывать), адаптер ждёт следующего хода-уведомления. Приходит ли такое уведомление в открытую stream-json сессию — НЕ ПРОВЕРЕНО.
  Это первая задача Ф5. **ЗАКРЫТО 21.09.2026 измерением — уведомление ПРИХОДИТ, см. дополнение ниже.** Осталось проверить то же для воркфлоу.
### Дополнение 21.09.2026 (веха В2): ИТОГ ФОНОВОГО СУБАГЕНТА ПРИХОДИТ. Измерено, а не выведено.

Эксперимент при записи фикстуры `test/fixtures/claude/06-subagent.jsonl`: после первого `result` с
`subagent_stats.started_in_background: 1` stdin держали ОТКРЫТЫМ 90 секунд и записывали всё, что придёт.
Пришло — и быстро. Через **4 мс** после первого `result` начался ВТОРОЙ ход: свой `system/init`, свои
`stream_event`, `assistant` с текстом `DONE` и свой `result` (`subtype: "success"`, `is_error: false`) на
**8002 мс** от старта против 6490 мс у первого. Итого 15 строк после первого `result`, процесс всё это
время жив, выход по закрытию stdin. Сырые данные — `06-subagent.jsonl` и `06-subagent.experiment.json`.

Следствия для дизайна:
- движок «claude-workflow» НЕ обречён быть «выстрелил и забыл»: наблюдение за фоновой работой в открытой
  stream-json сессии возможно. Первая задача Ф5 сужается до воркфлоу (субагенты закрыты);
- ловушка: `subagent_stats` НАКОПИТЕЛЬНЫЙ по сессии. Во втором `result` он ТОТ ЖЕ
  (`spawned: 1, started_in_background: 1, completed: 1`), поэтому момент «всё доделали» по счётчику не
  поймать в принципе. Адаптер В2 после каждого `result` с фоном ждёт отсрочку `subagentGraceMs`
  (по умолчанию 30 с), перезапуская её на любом новом событии, и завершает ход по ПОСЛЕДНЕМУ `result`;
  молчание всю отсрочку даёт `status.changed` с пометкой `subagent_grace_expired`;
- второе измерение того же дня: `system/init` приходит на КАЖДЫЙ ход, в том числе на второй ход в одном
  тёплом процессе. Значит `init` — маркер ХОДА, а не сессии, и `session.started` по нему можно слать
  только один раз.

- ТЁПЛЫЕ СЕССИИ — ОПТИМИЗАЦИЯ, А НЕ ОПОРА. С дешёвым профилем холодный старт `claude` — около 3 с, а не 15–60 с, как в мостах agent-chat (там грузился весь контекст рабочей папки). Выигрыш тёплой сессии — 1–2 с на реплику.
  Следствие для Ф1: пул тёплых процессов нужен интерактивному чату; ноды флоу могут стартовать процесс на ход с `--resume` — проще, устойчивее к обрывам сети и не держит десятки процессов. Решение по умолчанию для нод: процесс на ход.
- КЭШ ПРОМПТА ЖИВЁТ НА СТОРОНЕ API, НЕ НА ПРОЦЕССЕ. Спайк S1 показал тёплый кэш ещё через час простоя (`cache_read_input_tokens` не падает). Значит холодный процесс с `--resume`, запущенный в пределах того же часа, читает тот же
  серверный кэш — тёплый процесс экономит только ~2 с на старте, не токены кэша.
- АВТОПАМЯТЬ CLAUDE CODE ПИШЕТ МИМО INBOX (дополнение 28.09.2026, В5 — известный предел, не ошибка Пульта). Claude Code сам ведёт
  автопамять в `~/.claude/projects/<cwd с «-» вместо «/»>/memory/` (`MEMORY.md` и файлы заметок) — это встроенное поведение CLI, и в Inbox
  разрешений Пульта такая запись не попадает (механизм — почему `--permission-prompt-tool` её не спрашивает — не разбирали). Значит, агент Пульта может оставить заметку, которую
  прочтёт следующий разговор в той же папке (и терминальный `claude` там же), а в Inbox не будет ни строки. Инвариант 8 это не нарушает: пишет не
  Пульт, а немодифицированный CLI в свою папку. Пульт автопамять не выключает и не подменяет; общая память агентов Пульта — отдельный
  механизм Ф6 с записью только по команде человека (`10-PLAN-hermes-ideas.md`).
