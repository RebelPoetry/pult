# Идеи sandcastle в Пульте — решение лида (28.09.2026)

Источник: [mattpocock/sandcastle](https://github.com/mattpocock/sandcastle), MIT, v0.12.0, последний пуш 29.06.2026 (заброшен,
pre-1.0). Effect-TS, ADR + `CONTEXT.md`, песочницы Docker/Podman/Vercel/Daytona, по умолчанию `--dangerously-skip-permissions`.
Ниже — их решения против того, что уже есть в Пульте. Это разбор идей, не адаптер и не зависимость.

## Куда что встаёт

| Возможность | Как у нас | Когда |
|---|---|---|
| Сторож тишины на ход | нет отдельного таймера — только грейс субагентов и потолок повторов | Ф1.5, до крона Ф6 |
| Три стратегии веток `--worktree` | только create/reuse/remove, слияния нет | Ф4 «репо и ветки» |
| Правило переиспользования worktree | reuse не подтягивает и не проверяет отставание | Ф4, вместе со стратегиями веток |
| Словарь терминов + отклонённые фичи (`CONTEXT.md`, `docs/out-of-scope/*`) | решения по фазам, но не в этом формате | при следующей правке спецификации / старте Ф1.5 |
| Стартовые флоу для доски | шаблонов флоу пока нет | Ф3 |

### Сторож тишины на ход
`IDLE_RECHECK_MS = 60_000` в `claude`- и `codex`-адаптерах — это только повторная проверка страны выхода после простоя
(инвариант 2), не таймер на зависший ход. Реальный сторож у нас не сделан: есть `subagentGraceMs` (грейс ПОСЛЕ сигнала
завершения хода при фоновом субагенте) и потолок повторов `system/api_retry`, но ход без единого события журнала никто
не обрывает. sandcastle держит ДВА таймера (ADR-0019, `docs/adr/0019-completion-timeout-for-hanging-process.md`,
`src/Orchestrator.ts`): idle-таймер 600 с, сбрасывается КАЖДЫМ событием — тишина всю отсрочку = провал хода; после сигнала
завершения — короткий completion-таймер 60 с → успех с предупреждением, если процесс не вышел (держат stdout дочерние
`gh`/MCP). Взять оба таймера per-provider: idle сбрасывается на каждое событие журнала; «сигнал завершения» — `result` у
claude, `turn/completed` у codex, `session.idle` у opencode (адаптер ещё не написан, появится в Ф1.5). Числа 600/60 с —
стартовые, замерить под наш трафик, не переносить вслепую.

### Ветки `--worktree`
sandcastle даёт три стратегии (CONTEXT.md, ADR-0003): `head` (прямо в текущей папке), `merge-to-head` (временная ветка
сама вливается в HEAD вызывающего), `branch` (именованная, вливается вручную). Правило ADR-0018: fork изолирует ТОЛЬКО
сессию → параллельным агентам нужны разные ветки, иначе гонка за общий HEAD. У нас `src/sessions/worktree.ts` сейчас умеет
только завести/переиспользовать/удалить worktree — ни одной из трёх стратегий слияния нет.

### Переиспользование worktree
Текущий reuse (`worktree.ts:187-204, 211-217`): нашёл ту же ветку в `git worktree list` → взял папку как есть, если её не
держит другой агент. Про чистоту дерева и подтягивание изменений кода нет вовсе. sandcastle (ADR-0003): подтягивать
`git fetch` + `merge --ff-only` ТОЛЬКО когда дерево чистое И строго отстаёт от базы; иначе — брать как есть с явным
предупреждением; `reset --hard` не применяется никогда. Взять правило: перед reuse — чистота+отставание → ff-only merge,
иначе предупреждение в журнал вместо тихого молчания.

### Гигиена документов
`CONTEXT.md` — словарь терминов с колонкой «не называть так» (у нас это будет: сессия, ход, агент, провайдер, worktree,
Inbox…); `docs/out-of-scope/<фича>.md` — по файлу на отвергнутую фичу с причиной и условием пересмотра. Сами файлы в этом
PR не создаются — это задел на следующую правку спецификации или старт Ф1.5.

### Стартовые флоу для доски
Их шаблоны `parallel-planner`, `parallel-planner-with-review`, `sequential-reviewer` (`src/templates/*`) — годные образцы
для первых `.pult/flows/*.flow.json` в Ф3.

## Справочно (не план)
Точные строки запуска CLI у sandcastle — `codex exec fork` для новой ветки треда против `codex exec resume` для
продолжения (у них это ГЛАГОЛ, не флаг) — сверочный материал при проектировании собственного `pult agent`-CLI под форки,
не задача сама по себе.

## Не берём
- **Effect-TS и библиотеку целиком** — ноль рантайм-зависимостей: принцип Пульта; проект к тому же заброшен с 29.06.2026 и
  не дошёл до 1.0.
- **Контейнерные/облачные песочницы (Docker, Podman, Vercel, Daytona)** — у нас изоляция через git worktree, всё локально;
  поднимать рантайм песочницы незачем.
- **Обход разрешений по умолчанию (`--dangerously-skip-permissions`)** — прямо противоположно модели Inbox: разрешения у
  нас по умолчанию СПРАШИВАЮТ, а не пропускают.
- **Файловый лок worktree по PID (ADR-0007)** — проверено по коду, а не предположено: у нас один демон на `PULT_HOME`
  берёт эксклюзивный lock при старте (`acquireLock`, `src/daemon/server.ts:103-107`), и все операции с worktree идут через
  него же — гонка процессов за одну папку worktree и так исключена конструкцией, отдельный файловый лок был бы дублирующим.
- **Код под Windows** — вне платформ Пульта.
- **`EnvResolver`** — наш белый список окружения (`src/env/allowlist.ts`) строже их резолвера по умолчанию.
