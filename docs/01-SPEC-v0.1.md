## 0. Шапка

Заголовок h1: Пульт агентов
Подзаголовок: Диспетчерская над Claude Code и Codex: видно, что делает каждый агент, флоу собираются
из скиллов стрелками, всё работает на твоих подписках.
Мета-строка: system design + план · черновик v0.1 · 18.09.2026

Суть (абзац):
«Пульт» — desktop-приложение, которое само не разговаривает с моделями. Оно запускает официальные
`claude` и `codex`, в которые ты вошёл по подписке так же, как в терминале, и слушает их машинный поток
событий. Из этого потока строится всё остальное: живое дерево агентов, доска флоу, ветки по всем
репозиториям, расход лимитов.

## 2. Ключевое решение: Пульт — надстройка над CLI, а не свой клиент к API

Текст:
Есть два способа сделать такое приложение. Первый — ходить в API моделей самому. Тогда нужны API-ключи
и оплата по токенам, а подписка не работает. Второй — управлять готовыми CLI. Тогда вход по подписке
делает сам CLI, ровно как в терминале.

Что это даёт (список):
- Подписка работает без трюков: логинишься в `claude` и `codex` сам, Пульт только запускает их.
- Скиллы, хуки, MCP, CLAUDE.md и AGENTS.md работают как есть — их исполняет тот же CLI.
- Новые модели и фичи приезжают с обновлением CLI, а не с твоим релизом.
- Твой хук `block_dangerous_git.py` и тиры моделей продолжают действовать.

Чем платим (список):
- Зависимость от формата событий CLI. Лечится слоем адаптеров: вся «родная» специфика заперта в двух файлах.
- Правила провайдеров про сторонние оболочки над подпиской. Это главный риск, см. раздел «Риски».   <-- FACTS.md

Стек (короткая таблица «что — почему»):
- Electron + TypeScript — официальные SDK обоих провайдеров написаны под Node; Claude Desktop и VS Code устроены так же.
- React + xyflow (React Flow) — готовый редактор нод со стрелками, портами и миникартой.
- xterm.js — «сырой» терминал любой сессии как запасной вид.
- SQLite (better-sqlite3) — журнал событий и состояние флоу в одном файле.
- git CLI + gh — без библиотек-обёрток: worktree и PR проще и надёжнее через команды.

## 3. ДИАГРАММА B — путь одного события (sequence diagram)

Участники слева направо: Владелец · Окно · Flow Engine · Адаптер · CLI (`claude`/`codex`) · Event Store
Шаги:
 1. Владелец → Окно: «Запустить флоу»
 2. Окно → Flow Engine: run(flow, входные данные)
 3. Flow Engine → Git Service (можно показать заметкой): создать worktree и ветку для ноды
 4. Flow Engine → Адаптер: startSession(скилл, модель, усилие, папка worktree)
 5. Адаптер → CLI: запускает процесс, шлёт промпт
 6. CLI → Адаптер: поток «родных» событий (сообщение, вызов инструмента, старт субагента…)
 7. Адаптер → Event Store: те же события в общем словаре
 8. Event Store → Окно: push — дерево агентов растёт вживую
 9. CLI → Адаптер: «нужно разрешение на Bash: npm test»
10. Адаптер → Permission Broker → Окно (Inbox) → владелец: approve
11. Ответ тем же путём обратно в CLI
12. CLI → Адаптер: результат + расход токенов
13. Flow Engine: результат проверен по JSON-схеме → открывает следующие ноды
Подпись под диаграммой: «UI никогда не спрашивает CLI напрямую. Он читает журнал. Поэтому реплей,
поиск и подсчёт расхода получаются из того же журнала бесплатно — как чёрный ящик самолёта.»

## 4. Компоненты ядра (таблица: Компонент · Что делает · Что хранит)

- Session Manager · Запускает, возобновляет и останавливает процессы CLI. Одна сессия — один процесс в своей папке worktree. Держит процесс тёплым между репликами, чтобы не платить 15–60 с холодного старта. · id сессии провайдера для resume
- Provider Adapter · Переводит родной протокол CLI в общий словарь событий и обратно. Единый интерфейс: startSession, send, respondPermission, interrupt, resume. · версию протокола CLI
- Event Bus + Event Store · Каждое событие дописывается в журнал. Дерево агентов, реплей, расход и поиск — это разные запросы к одному журналу. · events (SQLite)
- Flow Engine · Превращает доску в граф без циклов и исполняет его: нода стартует, когда закрыты все входящие стрелки. Состояние прогона лежит на диске, поэтому прогон переживает закрытие приложения и лимит подписки. · flow_runs, node_runs
- Skill & Agent Registry · Сканирует `.agents/skills`, `.claude/skills`, `~/.claude/skills`, `~/.codex/skills`, `.claude/agents`, `.codex/agents`. Читает frontmatter, знает тир модели из `.claude/model-tiers.json`. · индекс скиллов и агентов
- Git Service · Репозитории рабочего пространства, worktree, ветки, дифф, PR через `gh`, статус CI. · привязку «задача → worktree → ветка → PR»
- Permission Broker · Собирает запросы разрешений из всех сессий в один Inbox. Правила на ноду: только чтение, правки в своём worktree, список разрешённых команд. · правила, журнал решений
- Quota & Failover · Следит за лимитами обеих подписок. При исчерпании ставит ноду на паузу до сброса окна или переводит на второго провайдера, если правило ноды это разрешает. · снимки лимитов
- Scheduler · Запускает флоу по расписанию: ночной прогон game-forge, утренний project-radar. · расписания
- Notifier · Системные уведомления и Telegram-бот: «нода ждёт решения», «PR зелёный», approve с телефона. · —

Врезка-пояснение (маленький блок «термины»):
- worktree — вторая рабочая папка того же репозитория на другой ветке. Два агента правят один проект и не мешают друг другу, как два стола в одной мастерской.
- DAG — граф без циклов: стрелки на доске не замыкаются в круг, поэтому у прогона всегда есть конец.
- журнал событий (event sourcing) — храним не «текущее состояние», а всё, что происходило; состояние вычисляется из журнала.

## 5. ДИАГРАММА C — пример доски флоу «Фича с двойным ревью»

Рисовать как настоящую доску нод: прямоугольные карточки с портами слева/справа, стрелки-кривые,
у каждой карточки бейдж провайдера и модели. Слева направо:

 [Триггер: вручную]
      → [Скилл: brainstorming · Claude · opus/high]
      → [Git: worktree + ветка feat/…]
      → [Агент: реализация · Claude · sonnet/medium]
      → веер на две параллельные ноды:
            [Ревью · Claude · sonnet/medium]
            [Ревью-челленджер · Codex · effort low]
      → [Сбор: находки обоих ревью]
      → [Гейт человека: владелец решает, что чинить]
      → [Агент: правки по ревью · Claude · sonnet]
      → [Shell: тесты]
      → [Условие: тесты зелёные?] — «нет» стрелкой назад НЕ рисовать (граф без циклов); вместо этого
         ветка «нет» ведёт в [Гейт человека: разобрать падение]
      → «да» → [Git: открыть PR] → [Git: ждать CI] → [Уведомление в Telegram]

Под каждой нодой мелко — статус прогона для живости (готово · идёт · ждёт тебя · в очереди), чтобы было
видно, что доска — это ещё и монитор: 3 ноды «готово», одна «идёт», гейт «ждёт тебя», остальные «в очереди».

## 6. Типы нод и контракт стрелки

Таблица «Нода · Что делает»:
- Триггер · вручную, расписание, новый коммит или PR, сообщение в Telegram
- Скилл · любой SKILL.md из реестра + провайдер, модель, усилие
- Агент · `.claude/agents/*.md` или `.codex/agents/*.toml`
- Промпт · свободный текст, когда скилла ещё нет
- Веер и Сбор · параллельные ветки и точка, где они сходятся
- Ревью другой моделью · один провайдер пишет, второй пытается опровергнуть
- Гейт человека · выбор из вариантов, approve, свободный ответ
- Условие · ветвление по полю ответа, например `verdict == "APPROVE"`
- Git · worktree + ветка, PR, ожидание CI, мёрж сквошем
- Shell · скрипт: тесты, `forge probe`, сборка

Контракт стрелки (абзац):
Стрелка — это не «передать весь чат». Каждая нода возвращает JSON по своей схеме и список файлов-артефактов.
Стрелка подставляет этот JSON в промпт следующей ноды. Порты типизированы: выход «находки ревью» нельзя
воткнуть во вход «ветка git». Так флоу остаётся дешёвым по токенам и предсказуемым.

Правило доски: нода без явной модели не запускается. Это твой `check_model_tiers.py`, встроенный в редактор.

## 7. Общий словарь событий (таблица: Событие · Когда · Что несёт)

- session.started · процесс CLI поднят · провайдер, модель, папка, ветка
- message.delta / message.done · агент пишет текст · текст, роль
- tool.called / tool.finished · вызов инструмента · имя, аргументы, результат, длительность
- agent.spawned / agent.finished · родился субагент · родитель, имя, модель, итог
- permission.requested / permission.resolved · агент просит разрешение · что именно, кто решил, как
- question.asked · агент задаёт вопрос человеку · варианты
- usage.updated · пришли цифры расхода · токены вход/выход, кэш, стоимость-эквивалент
- limit.hit · подписка упёрлась в лимит · провайдер, когда сброс
- git.changed · изменилась ветка, появился коммит или PR · репо, ветка, sha, PR, статус CI
- node.started / node.finished · нода флоу · id прогона, выход по схеме
- session.ended · процесс завершён · причина

Подпись: у каждого события есть session_id, parent_id и время. Поле parent_id и есть то, из чего рисуется дерево.

## 8. Идеи: что ещё добавить

Группа 1 — «Без этого нет продукта» (входит в MVP):
1. Живое дерево агентов. Сессия → субагенты → вызовы инструментов. У каждого узла модель, время, токены, статус.
2. Inbox решений. Все запросы разрешений и вопросы агентов из всех сессий в одном списке.
3. Задача = worktree = ветка. Агент никогда не работает в основной папке репозитория.

Группа 2 — «Ради этого уходят из терминала»:
4. Кросс-модельное ревью одной кнопкой. Дифф от Claude уходит челленджеру Codex и наоборот.
5. Лимиты подписок на виду. Автопауза до сброса окна или перевод ноды на второго провайдера.
6. Реплей сессии. Перемотка по таймлайну: что агент видел и что делал в этот момент.
7. Бюджет на флоу. Прогноз расхода до старта, стоп по порогу, отчёт «какая нода сколько съела».
8. Детектор конфликтов. Два агента правят один файл в разных worktree — предупреждение до мёржа.
9. Комментарий к строке диффа → реплика в ту же сессию агента.
10. Галерея шаблонов. Твои project-radar, diff-review, web-research и game-asset-generator как готовые доски.
11. Telegram-пульт. Approve, reject и статус с телефона.
12. Расписание флоу.

Группа 3 — «Позже»:
13. Эвалы флоу: прогнать N раз, сравнить выход и расход по моделям на одной ноде.
14. Импорт и экспорт: доска ⇄ Workflow-скрипт Claude Code. Твои `.claude/workflows/*.js` открываются как доски.
15. Единый менеджер скиллов, агентов и MCP для обоих CLI. Встроенный `sync_codex_agents.py`.
16. Панель артефактов: скриншоты forge, отчёты, сборки — привязаны к ноде, которая их создала.
17. Диета контекста. Показывает, сколько токенов сессия платит на старте за CLAUDE.md, агентов и скиллы, и предлагает воркерам пустую домашнюю папку.
18. Третий провайдер плагином: opencode с бесплатными моделями, локальные LLM.
19. Удалённый доступ: веб-морда по Tailscale.

## 9. ДИАГРАММА D — роадмап-лента и таблица фаз

Лента: 6 сегментов слева направо, ширина пропорциональна длительности, у каждого — название и срок.
Под лентой отметить ромбом «kill-проверка» после Фазы 0 и «сам пользуюсь каждый день» после Фазы 1.

Таблица (Фаза · Срок по вечерам · Что строим · Приёмка):
- Фаза 0 · Спайк · 3–5 вечеров · Скрипт на Node без UI: поднять `claude` и `codex` по подписке, получить поток событий, ответить на запрос разрешения, сделать resume, увидеть субагента. · Оба CLI проходят все пять пунктов. Если один не проходит — провайдер откладывается, а не проект.
- Фаза 1 · «Стеклянный терминал» · 3–4 недели · Electron-оболочка, список сессий, чат, живое дерево агентов, Inbox решений, журнал событий. Один репозиторий. · Неделю работаешь в Пульте вместо терминала и не возвращаешься.
- Фаза 2 · Репозитории и ветки · 2–3 недели · Рабочее пространство из нескольких репо. Задача → worktree → ветка → PR. Матрица «репозиторий × ветка × агент». Ревью диффа, статус CI. · Две задачи в двух репо идут параллельно и не мешают друг другу.
- Фаза 3 · Доска флоу · 4–6 недель · Редактор нод, реестр скиллов, типизированные порты, движок графа с состоянием на диске, гейт человека. Три шаблона из твоих воркфлоу. · diff-review собран на доске и даёт тот же результат, что скрипт.
- Фаза 4 · Лимиты и автоматика · 2–3 недели · Лимиты, failover, бюджеты, расписание, Telegram. · Ночной флоу переживает лимит подписки и утром отчитывается в Telegram.
- Фаза 5 · Выпуск · — · Решение: личный инструмент, опенсорс или продукт. · Принимается после 10 внешних пользователей, не раньше.

Врезка «Порядок важнее полноты»: дерево агентов и ветки дают пользу сразу и не зависят от доски.
Доска — самая дорогая часть, поэтому она третья, а не первая.
